# Устройство

## Схема

```
 POST /webhook/triage {"text"}      GET /form/triage-demo (форма)
 (песочница, evals и smoke)                     |
            |                                   |
   [Триаж: вход] Webhook ---+          +--- Form Trigger
            |               |          |        |
            |        Execute Workflow (ждёт результат)
            v                    |
   Respond to Webhook            v                Form (страница результата)
   (JSON, 200/400/429)   [Триаж: ядро] под-воркфлоу
                           Подготовка: проверка текста, маскирование, ключ клиента, режим
                           Data Table: создать triage_log, если нет
                           Data Table: строки за 24 часа
                           Cost guard ---- нельзя ---> Отказ (400/429)
                              | можно
                           есть ключ? -- нет --> Mock-классификатор
                              | да
                           LLM API #1 -> Проверка -> валидно? -- нет --> LLM API #2 -> Проверка
                              |                                                  (снова нет: needs_human=true)
                           Итог: строка журнала, повторное маскирование ответа модели
                              |
                           Data Table: записать --> [нужен человек или срочно?] --> Telegram (выключен)
                              |
                           Ответ (JSON + текст для формы)

 GET /webhook/board -> [Триаж: доска] Data Table: последние 20 + токены за сегодня -> HTML
```

## Ноды

Три воркфлоу лежат в `workflows/*.json` и импортируются через CLI n8n. JSON собирает
`scripts/build_workflows.py` из `src/`. В Code-ноде сначала идёт код самой ноды (функция
`main`), под ним только те объявления из `src/lib`, которые нода использует, с пометкой
«сгенерировано, не править». На холсте у групп нод есть заметки (sticky notes).

**Вход** (`triage-entry.json`)

| Нода | Что делает |
|---|---|
| Webhook POST /triage | принимает `{"text": "..."}` от песочницы на корне демо, evals и smoke; CORS только для своего домена и туннеля |
| Форма заявки | Form Trigger `/form/triage-demo`: одно поле и предупреждение про персональные данные; запросы без браузерного User-Agent получают 401 (`ignoreBots`) |
| Разбор (API), Разбор (форма) | Execute Workflow: вызывают ядро и ждут результат |
| Ответ API | Respond to Webhook: JSON и код 200, 400 или 429 |
| Ответ формы | страница с результатом, текст экранирован |

**Ядро** (`triage-core.json`, под-воркфлоу)

| Нода | Что делает |
|---|---|
| Подготовка | проверяет текст (пустой, длиннее 1000), маскирует контакты, считает HMAC-ключ клиента, выбирает режим llm или mock, читает лимиты из env, собирает тело запроса к модели |
| Таблица: создать, если нет | создаёт Data Table `triage_log_v2` при первом запуске |
| Журнал за 24 часа | строки для подсчёта лимитов и токенов |
| Cost guard | решает: принять, отказать 400 (плохой ввод) или 429 (лимит, бюджет) |
| Отказ | вежливое объяснение: какой лимит, когда попробовать снова |
| Есть ключ API? | без ключа, адреса шлюза или модели ветка уходит в mock |
| Mock-классификатор | заглушка по ключевым словам, 0 токенов |
| LLM API #1 | HTTP Request в `{LLM_BASE_URL}/chat/completions`, `response_format` json_schema (strict) |
| Проверка ответа #1 | разбирает `choices[0].message.content`, проверяет поля и ограничения, считает токены по `usage` |
| LLM API #2 (повтор) | тот же запрос плюс список ошибок первой попытки |
| Проверка ответа #2 | если и повтор не прошёл: `category=other`, `needs_human=true` |
| Итог | строка журнала; summary, next_step и city ещё раз проходят маскирование |
| Журнал: записать | вставка строки в Data Table |
| Нужен человек или срочно? → Telegram менеджеру | уведомление после записи; нода выключена до появления токена бота |
| Ответ: результат | JSON для API и экранированный текст для формы; в JSON — `meta.trace` (ниже) |

**Трасса в ответе API** (`meta.trace`). Code-ноды ставят метки `Date.now()`: «Подготовка» —
в начале и после маскирования, «Cost guard» — после решения, «Проверка ответа #1/#2» — при
получении ответа модели и после проверки, заглушка — после разбора. «Ответ: результат»
считает из них `timings_ms` (mask, limits, model, check, retry, route, total), собирает
сырые ответы модели по попыткам (ещё раз через маскирование), итог проверки, маршрут
(`manager` — жалоба, срочно, неясно; иначе `queue`) и счётчик лимита с адреса. Ноды, которые
в этом исполнении не запускались (заглушка, повтор), дают `null`. Отказ 400/429 несёт только
счётчик лимита: отказы в журнал не пишутся.

**Доска** (`board.json`): Webhook GET `/board` → последние 20 строк и токены за сегодня
из Data Table → HTML без скриптов и внешних ресурсов → ответ. У карточки метка режима
с именем модели (`llm · gpt-5.6-terra`), чтобы строки проверок на заглушке API
(`llm · fake-model`) не выглядели ответами модели.

## Почему так

**Два входа, одно ядро.** Form Trigger в n8n 2.x запрещает Respond to Webhook в своей ветке,
а вебхуку для evals нужен JSON с кодом ответа. Поэтому вход — отдельный воркфлоу с двумя
триггерами, а логика — под-воркфлоу «ядро», который вызывают обе ветки через Execute Workflow.
Ядро возвращает данные последней исполненной ноды. Ветка Telegram стоит на холсте выше
ветки ответа: в порядке исполнения v1 она идёт первой, последней остаётся «Ответ: результат».

**Логика в Code-нодах, исходники в `src/`.** Маскирование, mock, проверка ответа и HTML лежат
в `src/lib/*.js` и `src/nodes/*.js`. `tests/test_lib.js` проверяет функции, `tests/test_nodes.js`
исполняет собранные Code-ноды из JSON с заглушками n8n. Править JSON воркфлоу руками не нужно:
`deploy.sh` откажется деплоить, если JSON не пересобран.

**Вызов модели через HTTP Request, а не готовую ноду.** Запрос в формате OpenAI
`chat/completions` к адресу из `LLM_BASE_URL`: подходит любой OpenAI-совместимый шлюз,
провайдер и модель меняются настройкой, без правки воркфлоу. Тело: `model`,
`max_completion_tokens`, `temperature: 0`, системное сообщение и заявка,
`response_format` типа `json_schema` (strict), `reasoning_effort` — только если задан.
Нужны `usage` из ответа для учёта токенов и полный ответ с кодом статуса, чтобы ошибки
API шли в ту же проверку, что и битый JSON (`neverError` + `fullResponse`,
`onError: continueRegularOutput` на сетевые сбои). Адрес шлюза в ошибке сети вырезается
до записи в журнал. До 2026-10-05 здесь был Anthropic Messages API; ключа к нему не было,
и ветка удалена, чтобы не держать два формата.

**Structured outputs + своя проверка.** Схема задаёт форму JSON, но не выражает
`confidence` в 0..1 и «не больше 20 слов» в summary. Это проверяет `validateTriage`:
жёсткие нарушения, битый JSON, пустой `content` (так отвечает рассуждающая модель без
`reasoning_effort`), `refusal` и обрезка по `finish_reason: length` ведут к повтору запроса
с перечнем ошибок (один раз), после второй неудачи
ставится заглушка `category=other, needs_human=true`. Длинный summary обрезается до 20 слов
без повторного запроса. `needs_human` дополнительно выставляет правило: жалоба,
`confidence < 0.6` или контакт в ответе модели.

**Промпт-инъекции.** Текст заявки передаётся в теге `<заявка>`; теги `<заявка>` и `</заявка>`
внутри текста клиента вырезаются, чтобы текст не мог закрыть заявку и дописать свои правила.
Системный промпт называет текст данными. Если модель всё же поддастся, выход ограничен схемой
и проверкой: у воркфлоу нет инструментов и действий, худший исход — неверная метка или
произвольный текст до 300 символов в next_step (он виден только менеджеру, на доске текст
жалоб и неясных заявок скрыт).

## Cost guard

Хранилище — встроенная **Data Table** `triage_log_v2` (одна строка на обработанную заявку:
время, день, источник, HMAC-ключ клиента, результат, режим, модель, токены входа и выхода).
Static data не подошла: n8n читает её в начале исполнения и пишет в конце, параллельные
заявки затирают друг друга. Таблица `triage_log` (v1, с `cost_usd`) осталась от периода
учёта в долларах: колонки в существующую таблицу через ноду не добавить, поэтому новая.

Перед вызовом LLM ядро читает строки за 24 часа и считает:

| Проверка | По умолчанию | Ответ |
|---|---|---|
| заявок с этого клиента за час | `RATE_LIMIT_PER_IP_HOUR=5` | 429 `rate_limited_ip` |
| заявок за час через этот вход (форма и API отдельно) | `RATE_LIMIT_GLOBAL_HOUR=60` | 429 `rate_limited_global` |
| токенов сегодня + резерв на эту заявку > лимит | `DAILY_TOKEN_BUDGET=200000` | 429 `daily_budget` |

Общий лимит раздельный: скрипт, выбравший лимит API, не закрывает форму. Расход защищает
дневной лимит токенов, а не общий лимит.

Расход считается в токенах по `usage` из ответа шлюза: `prompt_tokens + completion_tokens`
всех попыток (рассуждения модели входят в `completion_tokens`). Цены провайдера в коде
не зашиты; если в `.env` заданы `PRICE_RUB_PER_1M_INPUT` и `PRICE_RUB_PER_1M_OUTPUT`,
ответ и доска дополнительно показывают рубли, иначе только токены.
Резерв — оценка сверху на две попытки: `2 × (900 + длина текста + max_completion_tokens)`;
системный промпт со схемой по замеру около 550 токенов, текст считается по токену на символ.
Лимит не будет превышен, пока исполнения идут по одному: `N8N_CONCURRENCY_PRODUCTION_LIMIT=1`,
иначе несколько параллельных заявок прошли бы проверку до записи друг друга.
Отказы не пишутся в журнал и не тратят токенов. «Сегодня» — по Москве.

Токен `X-Eval-Token` (`EVAL_BYPASS_TOKEN`, генерируется на сервере) снимает лимиты в час
для прогонов evals и smoke, и такие заявки не засчитываются в лимиты остальных.
Дневной лимит токенов он не снимает.

**Цена очереди.** В n8n 2.41.6 исполнения в режимах webhook, trigger и chat идут в одну
production-очередь (`concurrency-control.service.js`, `getQueue`), а вебхуки, форма и доска
запускаются в режиме webhook. При лимите 1 они исполняются строго по одному; под-воркфлоу
ядра (режим integrated) в очередь не встаёт. Очередь не ограничена,
отказ 429 тоже проходит через неё (лимит проверяется внутри воркфлоу). Поток GET на доску
или отклоняемых POST растит очередь, и настоящая заявка ждёт; в режиме LLM каждая заявка
держит слот до 2×30 секунд. Без лимита частоты и кэша доски на прокси это точка отказа.
Пример: `docs/nginx.conf.example` (limit_req, limit_conn, кэш доски на 20 секунд).

**IP.** n8n слушает только `127.0.0.1`, адрес клиента может сообщить только обратный прокси.
Какому заголовку верить, задаёт `TRUST_PROXY_HEADER`:

| Значение | Когда |
|---|---|
| `direct` (по умолчанию) | прокси нет; заголовки игнорируются, все заявки делят ключ `direct` |
| `x-real-ip` | nginx с `proxy_set_header X-Real-IP $remote_addr` (перезапись) |
| `cf-connecting-ip` | Cloudflare |
| `xff-last` | последний адрес `X-Forwarded-For`, его поставил ближайший прокси; так за Tailscale Funnel |

Caddy, cloudflared и Tailscale Funnel пропускают `X-Real-IP` клиента как есть, с ними
`x-real-ip` не ставить. Funnel ставит `X-Forwarded-For` сам, одним адресом клиента,
и заменяет присланный клиентом (`ipn/ipnlocal/serve.go`, `addProxyForwardedHeaders`).
За цепочкой CDN → nginx последний адрес XFF — это адрес CDN, и все посетители окажутся
под одним лимитом. В журнале хранится не IP, а HMAC-SHA256 с солью из `.env`, обрезанный
до 16 символов. Форма видит заголовки (`showHeaders`), ключ по адресу работает и для неё.

## Маскирование

`maskPII` (`src/lib/pii.js`) работает до сохранения и до отправки в LLM, а нода «Итог»
прогоняет через неё ещё и summary, next_step и city из ответа модели: контакт, записанный
словами, модель может переписать цифрами. Найден контакт в ответе — `needs_human=true`.

- ссылки на профили: `t.me`, `vk.com`, `wa.me`, `instagram.com`, `ok.ru` и др. → `[ссылка скрыта]`;
- email, включая кириллические (`иван@почта.рф`), без домена верхнего уровня (`ivan@gmail`),
  «ivan собака mail точка ru», «ivan [at] mail [dot] ru» → `[email скрыт]`;
- номера карт, 13–19 цифр → `[номер карты скрыт]`;
- паспорт РФ (4+6 цифр с пробелом или после слова «паспорт»), СНИЛС, ИНН после слова «ИНН» → `[номер документа скрыт]`;
- телефоны РФ в любой записи: `+7`, `8`, `(916)123-45-67`, `(495)123-45-67`, точки, пробел
  между каждой цифрой; международные с `+` → `[телефон скрыт]`;
- `@ники` и ники после «tg:», «тг», «телеграм», «инста», «skype», «ник» → `[ник скрыт]`.

Бюджеты («150 000 руб», «от 80 000-900 000»), даты, время, IP-адреса и короткие числа
не трогаются — это закреплено тестами. Что не ловится: телефон словами (в ответе модели
цифрами — ловится), «ivan at mail dot ru» без скобок, ник без @ и без слова-маркера,
паспорт без пробела и без слова «паспорт», адреса, ФИО. Поэтому форма прямо просит
не вводить персональные данные.

**Где остаётся исходный текст.** Выход триггера (вебхук или форма) n8n хранит в истории
исполнений. Успешные исполнения не сохраняются (`saveDataSuccessExecution: none`),
удалённые записи стираются из sqlite физически каждые 5 минут, ошибки живут 72 часа,
незавершённые исполнения формы закрываются через 10 минут. История доступна только
владельцу n8n.

## Публичная доска

- Весь текст пользователя и модели проходит через `escapeHtml`. Скриптов и внешних ресурсов нет,
  в `<meta>` стоит CSP `default-src 'none'; style-src 'unsafe-inline'; base-uri 'none';
  form-action 'none'` (встроенные стили разрешены). Свой CSP-заголовок n8n заменяет
  на sandbox-CSP для HTML из вебхуков.
- Модерация: у заявок со спамом, `needs_human=true` (жалобы, неясные) и с грубой лексикой
  (короткий стоп-лист в `src/lib/moderation.js`) текст на доске не показывается, только
  метки и причина. Заявка при этом принимается и разбирается.

## Безопасность ввода

- Страница результата формы: текст экранируется до передачи в n8n, n8n дополнительно
  прогоняет его через sanitize-html; двойного экранирования нет (`evals/checks.py`, фаза 2).
- JSON и urlencoded: до 1 МБ (`N8N_PAYLOAD_SIZE_MAX`). multipart/form-data n8n разбирает
  отдельно (formidable): файлы ограничены `N8N_FORMDATA_FILE_SIZE_MAX=1` (по умолчанию было
  200 МБ), а текстовые поля multipart этой настройкой не ограничиваются. Поэтому на прокси
  нужен `client_max_body_size 16k`. Текст заявки — до 1000 символов.
- Форма включена с `ignoreBots`: краулеры, превью ссылок и `curl` без браузерного
  User-Agent получают 401 и не создают заявок.
- Webhook `/triage`: `allowedOrigins` = домен демо и origin туннеля, браузеры на чужих сайтах
  не получат CORS-разрешение. Песочница зовёт его со своего домена. На прокси — `limit_req`,
  в n8n — 5 заявок в час с адреса, 60 в час на API и дневной лимит токенов.
- Песочница (`sandbox/`): статика без внешних ресурсов, CSP `default-src 'none'` со своими
  скриптом, стилями и запросами только на свой домен. Всё из ответа API вставляется через
  `textContent`.
- Тестовый ключ API в фазе 3 `evals/checks.py` ищется в файлах sqlite n8n и в логах
  контейнера после прогона; его там нет. Настоящий ключ и адрес шлюза ищутся до перезапусков
  в sqlite, в логах контейнера, обслуживавшего живые заявки, и в файлах проекта на сервере;
  их там нет.

## Компромиссы

- `N8N_BLOCK_ENV_ACCESS_IN_NODE=false`: Code-ноды читают лимиты и наличие ключа из env.
  Значит, владелец n8n через `$env` видит `N8N_ENCRYPTION_KEY`, соль, токен прогонов и ключ API.
  Аккаунт владельца ещё не создан: первый, кто откроет редактор, станет владельцем. Редактор
  доступен только через ssh-туннель; владельца нужно создать до любого прокси. Следующий шаг:
  ключ в credential n8n (Header Auth, `Authorization: Bearer …`), тогда он хранится
  зашифрованным, а env можно закрыть.
- Ключ и адрес шлюза приходят из общего файла сервера `../llm.env` (`env_file` в compose,
  `required: false`), за ним подключён `.env` проекта и перекрывает его. Поэтому в `.env`
  не должно быть пустой строки `LLM_API_KEY=`: она перекроет ключ пустым значением.
  `checks.py` пользуется этим порядком, чтобы временно подставить тестовый ключ и адрес
  заглушки, не трогая общий файл.
- Telegram-нода выключена: нужен credential бота и `TELEGRAM_CHAT_ID`. Уведомление уходит
  после записи в журнал, только для `needs_human` или высокой срочности; текст экранируется
  под `parse_mode=HTML`, ошибка Telegram не ломает приём заявки (`onError: continue`).
- Страница формы — шаблон n8n, он подгружает шрифт с Google Fonts. Доска внешних ресурсов
  не использует.
- Деплой останавливает n8n на время импорта (~30 секунд): CLI и сервер не должны
  одновременно писать в sqlite, а опубликованные через CLI изменения сервер подхватывает
  только после перезапуска.
- В n8n 2.x `publish:workflow` только ставит активную версию и кладёт задачу в outbox;
  сервер применяет её через несколько секунд после старта, и до этого под-воркфлоу
  исполняется старой версией. `scripts/wait_published.py` ждёт, пока версии совпадут,
  и только потом идёт smoke.
