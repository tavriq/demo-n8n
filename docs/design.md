# Устройство

## Схема

```
 POST /webhook/triage {"text"}      GET /form/triage-demo (форма)
            |                                   |
   [Триаж: вход] Webhook ---+          +--- Form Trigger
            |               |          |        |
            |        Execute Workflow (ждёт результат)
            v                    |
   Respond to Webhook            v                Form (страница результата)
   (JSON, 200/400/429)   [Триаж: ядро] под-воркфлоу
                           Подготовка: проверка текста, маскирование, HMAC(IP), режим
                           Data Table: создать triage_log, если нет
                           Data Table: строки за 24 часа
                           Cost guard ---- нельзя ---> Отказ (400/429)
                              | можно
                           есть ключ? -- нет --> Mock-классификатор
                              | да
                           Claude API #1 -> Проверка -> валидно? -- нет --> Claude API #2 -> Проверка
                              |                                                  (снова нет: needs_human=true)
                           Итог (строка журнала) -> [нужен человек или срочно?] -> Telegram (выключен)
                              |
                           Data Table: записать -> Ответ (JSON + текст для формы)

 GET /webhook/board -> [Триаж: доска] Data Table: последние 20 + расход за сегодня -> HTML
```

## Почему так

**Два входа, одно ядро.** Form Trigger в n8n 2.x запрещает Respond to Webhook в своей ветке,
а вебхуку для evals нужен JSON с кодом ответа. Поэтому вход — отдельный воркфлоу с двумя
триггерами, а логика — под-воркфлоу «ядро», который вызывают обе ветки через Execute Workflow.
Ядро возвращает данные последней исполненной ноды, поэтому ветка Telegram подвешена выше
ветки ответа: в порядке исполнения v1 она идёт первой, а последней остаётся «Ответ: результат».

**Логика в Code-нодах, исходники в `src/`.** Маскирование, mock, проверка ответа и HTML — это
обычные функции. Они лежат в `src/lib/*.js`, покрыты `tests/test_lib.js` и подклеиваются
в Code-ноды скриптом `scripts/build_workflows.py`. Править JSON воркфлоу руками не нужно,
`deploy.sh` откажется деплоить, если JSON не пересобран.

**Вызов Claude — HTTP Request, а не Anthropic-нода.** Нужны `output_config.format`
(structured outputs по JSON-схеме), `usage` из ответа для учёта расхода и полный ответ
с кодом статуса, чтобы ошибки API шли в ту же проверку, что и битый JSON
(`neverError` + `fullResponse`, `onError: continueRegularOutput` на сетевые сбои).

**Structured outputs + своя проверка.** Схема гарантирует форму JSON, но не выражает
`confidence` в 0..1 и «не больше 20 слов» в summary. `validateTriage` проверяет это сама:
жёсткие нарушения — повтор запроса с перечнем ошибок (один раз), после второй неудачи —
заглушка `category=other, needs_human=true`. Длинный summary не повод платить за повтор:
он обрезается до 20 слов. `needs_human` дополнительно выставляется правилом
(жалоба или `confidence < 0.6`), модель это поле не может «забыть».

**Промпт-инъекции.** Текст заявки передаётся в теге `<заявка>`, системный промпт называет его
данными. Даже если модель поддастся, выход ограничен схемой и проверкой: максимум неверная
категория, лишних действий у воркфлоу нет.

## Cost guard

Хранилище — встроенная **Data Table** `triage_log` (одна строка на обработанную заявку:
время, день, HMAC-ключ клиента, результат, режим, стоимость). Static data не подошла:
n8n читает её в начале исполнения и пишет в конце, параллельные заявки затирают друг друга.

Перед вызовом LLM ядро читает строки за 24 часа и считает:

| Проверка | По умолчанию | Ответ |
|---|---|---|
| заявок с этого клиента за час | `RATE_LIMIT_PER_IP_HOUR=5` | 429 `rate_limited_ip` |
| заявок всего за час (защита от смены IP) | `RATE_LIMIT_GLOBAL_HOUR=60` | 429 `rate_limited_global` |
| потрачено сегодня + резерв на эту заявку > бюджет | `DAILY_BUDGET_USD=0.50` | 429 `daily_budget` |

Расход считается по `usage` из ответа API: `input_tokens × цена входа + output_tokens × цена
выхода` (цены в `.env`, по умолчанию Claude Haiku 4.5: $1 и $5 за 1 млн токенов).
Резерв — оценка сверху на две попытки: `2 × ((900 + длина текста) × вход + max_tokens × выход)`.
Бюджет не будет превышен, пока исполнения идут по одному: `N8N_CONCURRENCY_PRODUCTION_LIMIT=1`,
иначе несколько параллельных заявок прошли бы проверку до записи друг друга.
Цена этого — очередь: доска ждёт, пока идёт вызов LLM (до 30 секунд таймаута).
Отказы не пишутся в журнал и не стоят денег. «Сегодня» — по Москве.

Токен `X-Eval-Token` (`EVAL_BYPASS_TOKEN`, генерируется на сервере) снимает лимиты в час
для прогонов evals и smoke, и такие заявки не засчитываются в лимиты в час остальных.
Дневной бюджет он не снимает: расход прогонов входит в общий счётчик.

**IP.** n8n слушает только `127.0.0.1`, поэтому адрес клиента может прийти только
от обратного прокси: берётся `X-Real-IP`, иначе последний адрес из `X-Forwarded-For`
(его добавил ближайший прокси, клиент его не подделает). Пока прокси нет, все запросы
приходят без заголовков и делят один ключ `direct`. В журнале хранится не IP,
а HMAC-SHA256 с солью из `.env`, обрезанный до 16 символов.

## Маскирование

`maskPII` (`src/lib/pii.js`) работает до сохранения и до отправки в LLM:

- email → `[email скрыт]`;
- номера карт, 13–19 цифр → `[номер карты скрыт]`;
- телефоны РФ (`+7`, `7`, `8` и 10 цифр, мобильные без префикса) и международные с `+` → `[телефон скрыт]`;
- `@ники` → `[ник скрыт]`.

Бюджеты («150 000 руб», «от 50 000 - 200 000 ₽»), даты и короткие числа не трогаются —
это закреплено тестами. Что не ловится: телефон, записанный словами или с нестандартными
разделителями, адреса, ФИО. Поэтому форма прямо просит не вводить персональные данные.

**Где остаётся исходный текст.** Выход триггера (вебхук или форма) n8n хранит в истории
исполнений. Успешные исполнения не сохраняются (`saveDataSuccessExecution: none`),
удалённые записи стираются из sqlite физически каждые 5 минут, ошибки живут 72 часа,
незавершённые исполнения формы закрываются через 10 минут. История доступна только
владельцу n8n.

## Безопасность вывода

- Доска: весь текст пользователя и модели проходит через `escapeHtml`, внешних ресурсов нет,
  в `<meta>` строгий CSP (`default-src 'none'`). Свой CSP-заголовок n8n заменяет
  на sandbox-CSP для HTML из вебхуков — страница открывается как изолированная.
- Страница результата формы: текст экранируется до передачи в n8n, n8n дополнительно
  прогоняет его через sanitize-html.
- Вебхук принимает до 1 МБ (`N8N_PAYLOAD_SIZE_MAX`), текст — до 1000 символов.
- Форма включена с `ignoreBots`: краулеры и превью ссылок (и `curl` без браузерного
  User-Agent) получают 401 и не создают заявок.
- Ключ API читается из env только в HTTP-ноде и не попадает в данные исполнения
  (проверено поиском тестового ключа по sqlite и журналам событий, см. `evals/fake-api-2026-10-05.json`).

## Компромиссы

- `N8N_BLOCK_ENV_ACCESS_IN_NODE=false`: Code-ноды читают лимиты и наличие ключа из env.
  Значит, любой, кто правит воркфлоу, видит env. Здесь это только владелец; публичного API
  (`N8N_PUBLIC_API_DISABLED=true`) и других пользователей нет.
- Telegram-нода выключена: нужен credential бота и `TELEGRAM_CHAT_ID`. Уведомление
  уходит только для `needs_human` или высокой срочности.
- Страница формы — шаблон n8n, он подгружает шрифт с Google Fonts. Доска внешних ресурсов
  не использует.
- Деплой останавливает n8n на время импорта (~30 секунд): CLI и сервер не должны
  одновременно писать в sqlite, а опубликованные через CLI изменения сервер подхватывает
  только после перезапуска.
- В n8n 2.x `publish:workflow` только ставит активную версию и кладёт задачу в outbox;
  сервер применяет её через несколько секунд после старта, и до этого под-воркфлоу
  исполняется старой версией. `scripts/wait_published.py` ждёт, пока версии совпадут,
  и только потом идёт smoke. Без этого шага smoke проверял бы старый код.
